libxisfconv , the library manual

Reading and writing XISF images from C, C++ and Python

libxisfconv reads PixInsight XISF, FITS and ASDF images into arrays and writes arrays as XISF, FITS, ASDF, TIFF or PNG. This manual shows how to use it from each of the three languages, with programs that ran on one real frame. What they printed is printed here.

Start here

What the library is, how to get it, and a first program.

One library, three languages

libxisfconv has one interface: the C API that include/xisfconv.h declares. The command line tool xisfconv is written on it and uses nothing else, so whatever the tool does, a program can do with the same calls.

  • C programs include the header and link the library. It is plain C99.
  • C++ programs include the same header. There is no separate C++ interface, and none is needed: forty lines of C++ turn the handles into objects that free themselves and the status codes into exceptions. From C++ shows them.
  • Python programs import the package xisfconv, which holds the library and calls it through ctypes. It is not a copy of the C API: images are NumPy arrays, failures are exceptions, options are keyword arguments.

The purpose of the library is XISF, and the conversion between XISF, FITS and ASDF. FITS and ASDF are supported as far as images need them; for tables and everything else in those formats, CFITSIO, astropy and the Python package asdf are the libraries to use.

Zstandard needs a build with libzstd; xisfconv_codec_available and xisfconv.codec_available say what a build has. The library and the Python package are under the LGPL, version 3 or later, so that programs under other licences can use them. The version is 0.x: the API may still change between releases.

Getting it

C and C++

Building needs a C++17 compiler, CMake 3.15 or later and zlib; libzstd is optional and recommended, because PixInsight can write Zstandard-compressed files.

cmake -S . -B build -DBUILD_SHARED_LIBS=ON
cmake --build build -j
sudo cmake --install build      # libxisfconv, xisfconv.h, xisfconv.pc, the CMake package, the tool

A program finds the header and the library through pkg-config, or through the CMake package:

cc app.c $(pkg-config --cflags --libs xisfconv) -o app
c++ -std=c++17 app.cpp $(pkg-config --cflags --libs xisfconv) -o app
find_package(xisfconv REQUIRED)
target_link_libraries(app PRIVATE xisfconv::xisfconv)

Without -DBUILD_SHARED_LIBS=ON the library is static. A static library comes with the pkg-config file only, to be used with pkg-config --static; the CMake package is installed with the shared library.

Python

pip install .                    # from a checkout: builds the library and installs the package
pip install ".[astropy]"         # the same, with astropy

The package needs Python 3.10 or later and NumPy. It brings its own copy of the library, so nothing else has to be installed. At the time of version the package is not on PyPI yet; once it is, pip install xisfconv does the same without a checkout.

A first program

The smallest useful program opens a file and says what is in it. It works on any file the library reads: FITS and ASDF are recognized by their first bytes, and anything else is taken for XISF.

Three things in it come back in every program. A context holds the text of the last failure, so the program can print it. Every struct is filled by its _init function before it is used. And what was opened is closed: by hand in C, by the handle in C++, by the with block in Python.

One thing the examples leave out. Text is UTF-8 everywhere in the library, file names on Windows included. A Windows program that takes file names from its command line gets them in the code page of the system unless it asks for them as wide characters (wmain) and converts them, as the tool does; the examples take the names as they come, which is right for names in ASCII.

From C++

The header is C++ as it stands: it wraps itself in extern "C". What a C++ program wants on top of it is that handles free themselves and that a failure is an exception. That is the namespace xisf below, taken from examples/tour.cpp. It is not part of the library: copy it into a program and change it to taste. The C++ examples in this manual use it.

One rule comes with it. The handlers a program gives to the library, for messages and for progress, are called from C: no exception may leave them. A lambda that captures nothing converts to the function pointer the API takes, and gets at the program's state through the void *user pointer that is passed along.

How the library works

The few rules that hold everywhere: failures, pixels, and what describes an image.

Contexts, failures and messages

The library has no global state and prints nothing. A program makes a context, and everything that happens is told to that context or to the handles made from it. A context and its handles belong to one thread at a time; a program with several threads gives each its own, and different contexts are independent.

C

Every function that can fail returns an xisfconv_status. XISFCONV_OK is 0, so a call is tested like any C call. The status says what kind of failure it was; the text for this one case is kept in the context until the next failure. Warnings and notes go to a message handler, if the program sets one, and are dropped otherwise.

C++

With the helpers of From C++, a call is wrapped in xisf::check, which throws xisf::Error when the status is not XISFCONV_OK. The exception carries the status and, as what(), the text the context has for it. Calls whose failure is an answer and not an error are tested by hand: Astrometry asks for a solution that an image may not have, and Progress, messages and failures stops a call on purpose.

Python

A call that fails raises xisfconv.Error, or the class below it for the kind of failure. Most of these classes are also the exception Python itself has for the case, so code that catches FileNotFoundError or ValueError catches them. There is no context to make: the package keeps one for each thread. Warnings of the library are Python warnings, and its notes go to the logger xisfconv.

The messages are those of the command line tool, and some name its options (--force, --bounds): the option names say which setting is meant. In Python the same messages name the arguments (overwrite=True).

Options

In C and C++, the options of a call are a struct. Each struct starts with its own size and is filled with its defaults by an _init function that is told the size the program was compiled with: xisfconv_read_options_init(&options, sizeof options). New fields are only ever added at the end, and the library reads no more of a struct than that size says, so a program built against an older header keeps working with a newer library. Where a call takes a pointer to options, NULL means the defaults. Enumerations are 32-bit integers with named constants, and flags are 0 or 1.

In Python the options are keyword arguments, with names in place of the constants: sample_format="float32", codec="zstd", row_order="bottom-up".

Pixels

An image is read and written as a whole, in memory. The table says how it lies there.

C and C++Python
LayoutOne buffer, planar: channel 0, all its rows, then channel 1, and so on. Host byte order. A NumPy array: [height, width] for one channel, [height, width, channels] for several. channels="first" gives [channels, height, width].
Row orderStated in every call that passes pixels: XISFCONV_ROWS_TOP_DOWN or XISFCONV_ROWS_BOTTOM_UP. Row 0 is the top of the image, as in Pillow and matplotlib. row_order="bottom-up" gives the FITS convention.
SamplesXISFCONV_SAMPLE_UINT8, UINT16, UINT32, UINT64, FLOAT32, FLOAT64; XISFCONV_SAMPLE_AS_STORED reads what the file has. The NumPy types of the same names; sample_format=None reads what the file has.

Asking for another sample format than the file has rescales; it does not cast. Integers go to integers over their full ranges, integers go to floating point as 0 to 1, and floating point goes to integers with the bounds of the image mapped to the full range of the integer. Only floating point to floating point is left as it is. The bounds are the range that floating point samples are meant to cover, 0 to 1 in most XISF files and 0 to 65535 in some; an image carries them, the stretch functions are told them, and writing takes them.

The files differ in which row comes first. XISF, TIFF and PNG store the top row first; FITS stores the bottom row first unless its ROWORDER keyword says otherwise. The library turns the rows as needed, which is why it always wants to know which order a buffer has.

Keywords and properties

Two kinds of data describe an image, and the library keeps both.

FITS keywords are cards of a name, a value and a comment, in order; XISF files carry them as well as FITS files do. In C a value is the text FITS writes for it, so a string comes with its quotes; xisfconv_keywords_get_text takes them off. In Python a value is a str, a bool, an int, a float, or None for a card without one. A keyword that was read and not changed is written back exactly as it was.

XISF properties are typed values with an id such as Instrument:Telescope:FocalLength: numbers, strings, time points, vectors and matrices. An image has them, and so has the file. PixInsight keeps the processing history and its astrometric solution there. Converted to FITS or ASDF, a file takes its properties along, and gives them back when it is converted to XISF again.

WCS keywords need one more thought, because they describe pixel positions and so depend on the row order. In an XISF file they count rows from the bottom, as PixInsight writes them, while the pixels are stored from the top. Astrometry shows the call that gives them for either order.

A tour on one frame

Running the tour

The chapters are the functions of one program per language: examples/tour.c, examples/tour.cpp and examples/tour.py. What is in a file

Opening a file reads its header and no pixels, so it is cheap for a file of any size. The file then answers questions: how many images, what size and sample format each has, how it is stored, and which keywords and properties it has.

The details that have a field or an attribute are the ones every format has. What only one format knows is asked for by name, as text: xisfconv_image_detail(file, 0, "compression") in C, image.detail("compression") in Python. The empty compression above says that this frame is stored as it is.

Reading pixels

Reading takes the number of the image, the sample format the program wants and the row order it wants. In C the program asks how large the buffer has to be, allocates it and has it filled. In Python the array comes back from the call.

The function read_float32 of the C and C++ versions is used by the chapters that follow. Beside the pixels it returns the range their samples are meant to cover, because that depends on what the file holds: floating point samples come as they are stored, with the bounds the image states, and integers come as 0 to 1. In Python, xisfconv.read_image returns the same range as the bounds of its image.

Stretching for the screen

A linear frame looks black: nearly all of its samples are close to the background. PixInsight shows such a frame through a screen transfer function, and the library computes it the same way. auto_stretch finds shadows, midtones and highlights from the data, with the shadows 2.8 normalized median deviations below the median and 0.25 as the target for the background. apply_stretch returns the stretched samples as 32-bit floating point from 0 to 1. Both are told the range of the samples they are given.

With a colour image, linked shares the statistics between the channels, which keeps the colour balance; unlinked stretches each channel for itself. A file may also carry the stretch its author saved: xisfconv_stored_stretch in C, image.stored_stretch in Python.

Writing an image

This chapter cuts 512 × 512 pixels from the middle of the frame, the square in the picture at the top, and writes them as a new XISF file with keywords, four properties, compression and a checksum.

The keywords are not simply those of the frame. A part of a frame is another image: what the cards say of the instrument and the observation holds for it as well, but WCS keywords and BAYERPAT say where a pixel is, and for the part they would be wrong. The chapter takes the cards it knows to hold by their names, and adds two of its own. The range of the samples is given along for the same reason: left out, it would be guessed from the pixels of the part.

The format follows the name of the file: .xisf, .fits, .asdf, .tif or .png. A file is written under its name with .part added and renamed when it is complete, so a call that fails leaves no half-written file under the final name. An existing file is replaced only when the call says so.

In C and C++ a writer collects images and writes them when it is finished: one image here, several for an XISF file with several images or a FITS file with several HDUs. The writer copies what it is given, so the program may free its buffers as soon as the image is added. In Python, xisfconv.write takes one array, one Image, or a list of them.

Converting files

One call does what the command line tool does with a file: it reads every image, turns the rows as the output format wants them, takes keywords and properties along, translates the astrometric solution, and writes the output.

The second conversion is how the picture at the top of this page was made. A smaller picture is the mean of the pixels it covers, taken before the stretch. From XISF, the call converts to FITS, ASDF, TIFF and PNG; from FITS and ASDF, to XISF, to each other, and to TIFF and PNG. XISF to XISF is the next chapter.

Rewriting and verifying

A rewrite stores the data blocks of an XISF file another way: compressed, or not, with checksums added or removed. It converts nothing. Pixels, keywords and properties come out as they went in, and unless told otherwise the call reads its output back and compares every block with the input.

The frame shrinks from 65.7 to 48.3 megabytes. Two blocks were compressed: the pixels, and the thumbnail PixInsight saves with them. xisfconv_rewrite_in_place and xisfconv.rewrite_in_place do the same to a file under its own name, and leave the file alone when it is already stored as asked.

Distributed units

XISF allows an image to live in more than one file: a header file, .xish, which is the XML header and nothing else, and the files that header names, where the data is. The library writes the data into one data blocks file, .xisb, beside the header. A program only ever names the header file. PixInsight itself opens monolithic files only, so the last step of the chapter packs the unit into one file again.

A header is data that came from somewhere, and it says which other files are read. So the library follows a header only as far as it is allowed to. By default that is to files in the directory of the header and below it, and only from a file that is named as a header file. To anywhere on the machine, or to no other file, is a setting: of the context in C and C++, xisfconv_context_set_external_files, and of each call in Python, external_files=. A block the header is not followed to is not read, and the failure says that this is the reason: XISFCONV_ERR_NOT_ALLOWED, or xisfconv.NotAllowedError, which is a PermissionError. Nothing is ever fetched from a network. A program that opens files from people it does not know should leave the default as it is.

Astrometry

PixInsight stores the astrometric solution of an image as XISF properties, with its distortion as surface splines. Other software expects WCS keywords. xisfconv_wcs_keywords and image.wcs_keywords() give them for the row order the program asks for: those the file has, or new ones made from PixInsight's solution, with the distortion fitted as SIP polynomials.

The example frame has not been plate-solved, so the call says that there is nothing to make keywords from. That answer is a status of its own, XISFCONV_ERR_NOT_FOUND, and xisfconv.NotFoundError in Python. On the same frame after PixInsight's ImageSolver has solved it, the chapter prints this:

Progress, messages and failures

Long calls report their progress to a handler, and the handler can stop them. A call that is stopped leaves no partly written file. The chapter also shows what a failure looks like, and how the notes of a conversion reach the program: it converts the frame to FITS and that file back to XISF, and prints what the library has to say about both.

In C and C++ the progress handler returns something other than 0 to stop the call, which then returns XISFCONV_ERR_CANCELLED. Another thread can ask for the same with xisfconv_context_cancel, the one function that may be called while a call runs in the context. In Python the handler stops the work by raising, and the exception comes out of the call; Ctrl-C does the same.

More for Python

Two modules for programs that already speak another interface: astropy's, and that of the xisf package.

With astropy

Importing xisfconv.astropy registers the format xisf with astropy's unified I/O, so that CCDData.read and CCDData.write take XISF files; read_hdulist and write_hdulist do the same for astropy.io.fits. Everything in this module follows the FITS conventions, as astropy does: row 0 of an array is the bottom of the image, a colour image is [channels, height, width], and the header describes the pixels that way, WCS included.

The header has eight cards more than the file has keywords: the six with which a FITS file describes its data (SIMPLE, BITPIX, NAXIS, NAXIS1, NAXIS2, EXTEND), and EXTNAME and ROWORDER. For a file with instrument and observation properties and no keywords for them, the keywords derived from those properties come on top. The data is big-endian because astropy's own FITS reader made the array; the image is handed to it as a FITS file in memory, which takes about four times the size of the image.

For programs written for the xisf package

The xisf package of Sergio Díaz is the usual way to read and write XISF in Python. xisfconv.xisf has a class of the same name, with the same methods, arguments and return values, so that a program written for that package runs on this library with its import line changed. None of that package's code is used. The reference of the module lists where the two differ on purpose.
